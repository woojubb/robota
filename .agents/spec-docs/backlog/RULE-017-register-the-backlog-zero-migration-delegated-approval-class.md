# RULE-017: register the BACKLOG-ZERO-MIGRATION delegated approval class

## Problem

The owner authorized repeated documentation-only batches that migrate the finite 2026-08-28 local
backlog to canonical GitHub issues or terminalize records whose outcomes were already delivered. The
delegated-class registry remains empty, so every later batch would either need ceremonial DIRECT
approval or would falsely claim a CLASS route that no registered class supports.

The empty registry is not the only gap. `standing-delegation-evidence` currently parses only the class
ID and registration date from a row. A DIRECT approval can omit its rule-declared `Given`; a CLASS
approval can omit `Given` and `Evidence condition met` or cite an instruction different from its
registry row; and duplicate/incomplete rows are not all rejected. Registering a broad migration class
without closing that structural gap would make the most important boundary evidence optional.

Reproduction on the integration base: `node scripts/harness/scan-standing-delegation-evidence.mjs`
reports `0 registered class(es)`, while `classifyApproval` returns a passing route for fixtures that
omit DIRECT `Given`, omit CLASS `Given` plus `Evidence condition met`, or use a CLASS instruction that
does not match the registered authorising instruction.

Source initiative: https://github.com/woojubb/robota/issues/2404. This work does not implement that
issue's history-aware durable-queue lifetime scan or any migration batch.

## Prior Art Research

Waived: RULE-012 already researched and adopted the delegated-class mechanism from pre-authorized ITIL
standard changes and AWS IAM permissions boundaries. RULE-017 registers one concrete instance of that
existing mechanism and closes a local evidence-form enforcement gap; it introduces no new approval
model that needs separate prior-art selection.

### Alternatives Considered

1. **Add only the registry row.** Pro: smallest diff. Con: CLASS approvals can still omit the row's
   declared provenance/evidence fields, so the authorization boundary is prose-only at its highest-risk
   point.
2. **Register the row and enforce structural completeness.** Pro: the existing scanner can prove that
   every row and CLASS approval carries the fields the rule declares mandatory, while reviewers retain
   semantic judgement. Con: requires focused scanner/test changes. Chosen.
3. **Have the scanner decide semantic scope compliance.** Pro: maximum automation. Con: a path regex
   cannot prove issue equivalence, delivery, other-session ownership, or evidence quality and would turn
   a judgement boundary into a misleading proxy. Rejected.

### Decision

Choose alternative 2. Register `BACKLOG-ZERO-MIGRATION` as a finite historical class whose eligible
population is derived directly from the exact Task/spec paths and blob OIDs at `origin/develop` OID
`2c875dd3ec6938d6eb0563b50c40d1f116fb4e7e`. The `/tmp` snapshot is a discovery aid only and is not
authorization evidence. Before approval, each batch spec commits a `## Migration Manifest` section of
at most six units and 15 tracked paths; one unit may contain a Task, a spec, or both. Each row records a
unit ID, original path/blob OID, exact issue/comment or delivery evidence, criterion-level disposition,
current branch/worktree/PR/session ownership and reservation checks, and every frozen-baseline
old-to-new key. Any manifest change after approval requires a new approval.

Each manifest row must prove exactly one disposition:

- unfinished work has one equivalent OPEN canonical GitHub issue and an append-only handoff comment
  containing decisions, evidence, remaining criteria, dependencies, resumption instructions, original
  paths, and source blob OIDs before every applicable Task `skipped` and/or spec `rejected` record cites
  the same exact `returned_to_issue:` comment URL; or
- delivered work identifies the exact historical criteria, maps each criterion to merge/current-tree
  evidence, and proves its merge commit is an ancestor of fresh `origin/develop`; every applicable Task
  and/or spec then terminalizes independently without rewriting historical verdicts.

Status alone is not current ownership: stale `active` or `blocked` records remain eligible when no live
branch, worktree, PR, session ownership, or reservation exists. Current ownership/reservation or a
source-blob mismatch excludes the unit from that batch. Deletion is never terminalization. Related-only
or umbrella issues are never treated as exact owners.
New issue creation must use an ID-bearing title and idempotency marker, then read back uniqueness before
local terminalization. The class permits only the named Task/spec lifecycle documents, its loop-run
records, and no-growth exact-path rekeys of already-existing frozen baseline entries. It does not permit
new baseline exemptions or any rule/policy change, including edits to this registry. It permits issue
creation and append-only evidence comments only; issue edit/delete/reopen/transfer/metadata changes and
issue closure are outside the class.

The scanner will enforce unique, complete registry rows; DIRECT `Given`; CLASS `Given` and
`Evidence condition met`; exact CLASS-to-registry instruction matching; and date ordering. It will not
infer semantic scope compliance; the proposal/approval guardian must read the committed manifest,
current GitHub state, current branch/PR/worktree/session reservations, source blobs, and whole diff.
This placement preserves the existing SSOT and enforcement owner and was validated against the parser,
all current approval consumers, the 2026-08-28 snapshot, post-snapshot GitHub delta, and adversarial
self-approval/duplicate/destructive-migration cases.

## Fallback & Degradation Declaration

None

## Solution

1. Replace the empty registry sentinel with one row whose class ID, finite scope, evidence condition,
   exact verbatim instruction, and registration date are all non-empty and parseable.
2. Extend the existing registry parser to retain the row's scope, evidence condition, instruction, and
   date and reject structurally incomplete or duplicate rows.
3. Extend approval classification to require non-empty DIRECT `Given`, non-empty CLASS `Given` and
   `Evidence condition met`, and an exact match between the CLASS entry's instruction and the registry
   instruction while preserving existing route/date/baseline behavior. Do not add a semantic path or
   issue-equivalence proxy.
4. Add pass/fail fixtures for the live row, pre-registration approval, incomplete/duplicate rows,
   missing DIRECT/CLASS evidence fields, mismatched CLASS instruction, and a complete post-registration
   approval; prove each new refusal branch red.
