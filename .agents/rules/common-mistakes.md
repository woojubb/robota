# Common Mistakes

Mistakes observed repeatedly in this codebase, each stated as the invariant to obey.
Parent: [AGENTS.md](../../AGENTS.md) | Index: [rules/index.md](index.md)

An entry is a compact row: the mistake, the correct approach, and — where they exist — a
`Worked example:` path showing what obeying looks like and a `Mechanized:` pointer to the check that
enforces it, with its suppression syntax. Those two are instruction and belong here.

What does NOT belong here is the incident: the date, the task or pull-request identifier, the
retelling of how it was discovered. That material belongs in the record that owns it, and a reader
must be able to obey an entry without opening anything else — see
[rules/index.md](index.md) § "How a rule is written". No entry carries such narrative now, and
`scan-rule-case-narrative` holds it there: a citation added to any rule document fails the scan
unless it links to a record that exists, sits in a fenced specimen, or declares its reason.

Numbering is stable and gapless — external references like "common-mistakes #9" must keep resolving,
so an entry is rewritten in place and never renumbered or deleted.

This is worse than an ordinary error: a message is what the next person trusts INSTEAD of reading the diff, so a false one does not merely fail to inform, it substitutes for looking. **Fix**: describe what the tree now contains, verified by reading it back — `git diff --cached`, or the file itself — never what the edit was meant to do. An editing script that reports success is not the tree agreeing. **Mechanism:** `ci:commitlint` (the `claims-resolve` rule: a commit-ish token must name an object, and a code-spanned repository path must exist in the tree or in this commit). |
| 86 | **Publishing a size the code did not measure.** A check reports how much it examined — files walked, records validated — and the number comes from a collection of results, a configuration entry, a static table, or one of the two walks it actually does. Nothing downstream re-derives it, so it can be wrong by any amount in either direction and every consumer still reads a healthy check. The counter is also routinely the one output nobody tests, and the two ways of half-testing it both pass on a broken one: a lower-bound assertion admits every over-count, and an assertion taken before the second run describes the first one and holds whether or not the counter resets. **Fix**: increment at the traversal, one number per population, and test the counter as the output it is — an exact value against a fixture of known size, plus an assertion taken AFTER a second run. **Mechanism:** `measurement-provenance` in `pnpm harness:scan`; the rule is [measurement-provenance.md](measurement-provenance.md). |
| 87 | Opening a pull request before the work is complete, then pushing the rest | Every push to an open PR re-runs CI **and re-triggers the reviewer**. Finish the whole unit locally first — implementation, the task file's outcome and evidence, archival, a green scan — then push once and open the PR. After that, push only to answer a finding or a red required check. A PR that gets three review rounds because three pushes happened has spent three review cycles on one diff. **Mechanism:** none — no check can tell a finished unit from an unfinished one, and refusing every second push would block the review-response case this rule depends on |
| 88 | Pushing a guessed cause for a red CI check instead of diagnosing it locally | Read the failing job's log and reproduce the finding against the local tree BEFORE the next push. A guess costs a full CI round trip plus a review round to be told it was wrong, and the second guess costs another. Where the failure class is mechanically detectable locally, add the floor rather than the habit. **Mechanism:** none — the enforcing check is the pre-push hook `.claude/hooks/pre-push-check.sh`, which refuses a branch whose lockfile differs with no manifest change (`LOCKFILE_CHURN_ACK=1` declares a deliberate resolution change); this field is verified against registered scans, lint rules and CI jobs, and a hook is none of those |
| 89 | **Taking a baseline with the tool that does the checking absent.** A check is added, its current findings are measured to prove it lands green — and the measurement runs on a machine missing an OPTIONAL dependency the check silently degrades without. The number is then a statement about the local environment, not about the tree, and it is wrong in the direction that reads as good news. Measured in one session, twice in the same change: `actionlint` printed `Rule "shellcheck" was disabled` and exited 0 locally, so "zero problems" was recorded and the job went red on its first CI run — where the finding was a `# shellcheck disable=... -- reason` directive that shellcheck cannot parse, and which had therefore been switching off EVERY check on its block rather than the one it named. **Fix**: before believing a baseline, make the tool report what it actually ran — `--verbose`, a rules listing, an examined-size line — and check that the optional halves are on. If the check asserts a dependency in CI, assert it locally too, in the same run that produces the number. **Mechanism:** none — the degradation is inside a third-party tool and reports success; the repository-side floor is the CI job's own `command -v` assertion, which is a workflow step and not a registered scan |
| 90 | **Repeating a recorded constraint instead of re-deriving it.** A task, spec or comment states why something cannot be done — a count too large, a flag unset, a credential absent, a check that would refuse — and the next agent carries that sentence forward as the reason to defer, narrow or refuse. The sentence was true when written and is a claim about THAT DAY. Measured across one backlog sweep: a "type-aware finding flood" was 6 violations; "1798 warnings" was 2093; "`REGRESSION_RED_PROOF_ENFORCE` set in no workflow" had been set for two weeks; a table of six hook/scan divergences had four already fixed; two spellings listed as guard holes were commands bash itself rejects; "the only closing condition" was a case that cannot fail; and "this agent has no repo-admin scope" was `permissions.admin: true`, asserted three times without one API call. Implementing from the record would have fixed problems that no longer existed and refused work that was permitted. **Fix**: before acting on a recorded constraint, RUN it — the count, the grep, the permission read, the completion condition — and record the new number beside the old one rather than replacing it, so the next reader sees the drift as well as the value. A constraint cited as the reason for NOT doing something deserves this most, because nothing downstream will test it. **Mechanism:** none — a recorded constraint is prose about an arbitrary subject, so no check can re-derive it in general; the nearest partial floors are `unearned-done-claims` and `measurement-provenance`, and neither reads a constraint stated in a Problem or Direction section |
