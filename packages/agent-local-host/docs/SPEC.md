# Local host authority

## Purpose

Provides Node hosts with the local authority needed to share secure runtime custody without importing a product entry point: the keyring file store, the key holder that is a process's only place for unlocked keys, the artifact sealers built on it, the passphrase rule, the owner-private session directory and control carrier through which a supervised runtime is registered and reached, the proof that a registered runtime is the daemon serving a workspace, the table that gives every command of that control socket its plain and its secure admission, the carrier through which a terminal of the same user drives or observes a session over it, how a runtime takes what its launcher hands it (the WebSocket token, its spawner's pair), the custody that decides who may act as a secure runtime's owner and whether its read keys are open, the rule that ends a runtime nothing certified, the workspace-root broker that retains the folders a person approved and performs project file operations against them, the launcher that starts one broker per user-state root, the trust service whose only project file port crosses that broker, the one physical root secure clients and runtimes fence and the fence they hold on it, and the loopback server that shows a product's built web GUI only after a one-time access code. Any product composition root that protects local state composes these; none of them chooses a product path, and only the GUI server asks a person for anything: the access code the product printed.

## Contract

A keyring store reads a regular file, refuses links and foreign ownership where the host can verify ownership, and bounds input before parsing it. A mutation uses a file lock and checks the expected keyring before replacement. The store verifies the result and reports a failure when it cannot confirm the write; a reported failure may still have changed the file.

Supervised-runtime registrations are untrusted discovery metadata. A registration is read only from an owner-private directory and from a regular file the user owns, never through a link. A runtime is controlled only after its recorded process start time proves it alive and the selected generation still matches, and a daemon is named only after an authenticated status exchange reports that it serves the workspace. A registration that is not known dead and whose control cannot be proven refuses discovery instead of being skipped, and two daemons for one workspace refuse as ambiguous. Each command of the control socket has one row saying what it admits in plain mode and in secure mode, so a command added without a decision does not compile; in secure mode a program of the same user keeps only what costs the owner at most a stopped runtime, and the rest is reached only inside an owner link, which the runtime's custody admits by what the link proved. Before anyone certified the runtime only its spawner is admitted: it may start sessions and drive them, never list, switch to, rename or delete a stored one, and it may certify the runtime once, after which every spawner link ends and none is admitted again. From then on only the owner is admitted, and it opens the runtime by handing it read keys over the link. What takes the keys away is the owner's own request, the last attached client or grant owner going, a lock command that needs no proof, because taking access away is something anyone who could stop the runtime can do, and fifteen minutes in which the owner did nothing; every change is told to every link. A runtime that nothing certified ends itself when no spawner links to it in time, and when its spawner leaves without certifying it, at once when idle and otherwise when the work it runs ends. An attached terminal or an owner link's session is one more surface under the session's own co-drive, prompt and session-switching rules and never an operator approver (an observer never submits or answers), so a connection that needs one is still refused, and a reader that stops reading loses only its own connection. A runtime takes its WebSocket token only from the pipe its launcher handed it and answers its spawner's pair before it starts any process; what arrives is checked exactly, nothing that was read is echoed, and a runtime told to expect either never falls back to another.

The workspace-root broker retains the exact folder object a person approved, and every project file operation compares its opened root with it. A broker lives only as long as the user-state root its approvals belong to and leaves nothing under its shared directory when that ends, so removing that root, like a broker or OS restart, requires one new approval per root. Because it holds the project root it also takes the checkpoint writer's exclusive lease, its atomic directory claims and the removals that let deleting a project session take everything the session left; a lease ends when its trust lease is revoked, when the broker closes or when the process that took it is gone, so a crashed client never leaves a live-looking writer owned by the long-lived broker. A start claims the root's namespace directory before it launches anything, so a sweep of the directories that gone brokers left can never read a starting broker's directory as left over; it attaches to a live broker instead of launching a second, and only to an endpoint that answers. The trust service grants only a root a person approved through a prepared candidate, and every read, write, directory operation and writer lease of a trusted root crosses the broker, so the host never touches a project file directly; a guarded checkpoint operation runs only while the broker still holds its writer lease. Secure clients and runtimes fence the same physical Git root, or the exact folder outside one: a fence holds that folder through its own descriptor together with the broker's trust generation at admission, and refuses a folder replaced under the same name, a changed trust generation and a Restricted choice that no longer names the displayed folder.

## Invariants

The GUI server treats every local program as hostile: the page that carries a runtime's credential, and a product API beside it, are served only to the browser that exchanged the access code for its path-scoped cookie, never to a request whose Host is neither loopback nor the one public host a TLS reverse proxy on the same machine publishes it under (the server itself never listens beyond loopback, and over https its cookie is Secure), and never from outside the web root; an API request that changes something also carries a header no cross-site form can set; a login can return to a named view only within its newly minted session; the host can keep the GUI unavailable until its runtime is ready; no request can crash the process serving it. A product may name one landing path for a browser another site sends back, such as an authorization server's redirect: it is served without the cookie, which a strict cookie would not send on such a redirect, but under the same Host rule, to a GET of exactly that path, with only the fixed page the product's handler returns, so what admits a request is what that handler checks, such as a one-time `state`.

The key holder offers operations on the keys, never the keys themselves, so every way of locking ends in one place and a lock ends every way of reading, the data keys of writer epochs included. Sealing needs only the public key and works while locked; opening and authorship need the holder unlocked. No sealer error carries plaintext, a key or a path, and a swapped sealing key is never accepted quietly.

A runtime's custody admits a link by what it proved and nothing else: a spawner never holds read keys, its authority ends at certification before any frame batched behind the certification can run, and a lock retires every link admitted before it, so an older link can never install a delayed grant or keep a decision open.

The store never logs or reports keyring content. It rejects an observed change to the expected keyring before replacement. A workspace daemon prover holds one authenticated handover at a time, and a failure to close a link permanently faults it.

## Non-goals

The store does not choose product paths, collect a passphrase, unlock a keyring, or decide which process receives owner authority. The composition root owns these decisions. The broker cannot authenticate a person over its same-user IPC, so a direct local client can create a new approval; asking the person is the composition root's. The prover does not authenticate a control link itself: the opener the composition root supplies must authenticate the selected binding before it returns a link.

## Design decisions

From the first unlock in a process the key holder seals to the sealing key that unlock verified, locked or not, even when the repair of the file cannot be written. Before that first unlock a locked writer can only seal to the key the file holds; that is an accepted weakness, caught at the next unlock and visible meanwhile through the fingerprint. An append-only writer reuses one data key per store for a writer epoch because one public-key operation per line was measured too slow to read back; the epoch ends as soon as the verified key is not the one its data key was sealed to, and at every lock, because a writer's data key reads every line sealed under it and so is key material like any other.

The lock can be taken over after its stale bound even if its former holder is still alive. The final ownership and content checks are separate from the filesystem replacement, so a stalled or non-cooperating writer can change the file between them. The store does not provide an atomic compare-and-swap or an unconditional guarantee against restoring an older keyslot. On filesystems without hard links, creation also relies on a separate absence check and replacement.

A broker started by an older host refuses an operation added since as malformed, having done nothing, and the protocol version stays fixed because a bump would break the check that finds a live broker; telling the person to restart that broker is the composition root's. How a host runs its own binary as a broker is a function it supplies, not a command line the package builds, because the argument layout and the start bound belong to the binary that serves the broker; the package asks it only when no broker answers, so a live broker costs the host no launch work.

The idle lock counts only what a person does (sending a prompt, answering what the session asked, changing the session or its settings), because it exists for an owner who walked away: a viewer left open on a screen nobody watches would otherwise keep the keys open for as long as it pages or refreshes. Every session message and every control command has one row saying which it is, so one added without a decision does not compile. A runtime nothing certified follows events, never a poll, and once its spawner is gone it still lets the work it runs end before it stops, because it was started by a spawner for an owner and is useful to nobody until certified, yet stopping it mid-turn would cut that work short.
