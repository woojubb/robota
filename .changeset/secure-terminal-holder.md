The terminal UI now starts while secure conversations are on; before, it exited with `Secure conversation sealing key holder is unavailable; no conversation store may open.` before showing a prompt, and the `/unlock` and `/lock` commands the documents describe could not run in any process. It starts on a locked key holder, like print mode, `acp` and `mcp serve`, so what it writes is sealed to the keyring and it asks for no passphrase to start. `/unlock` (yours alone, never the agent's) asks for the passphrase at the secret terminal and opens the keys in that terminal's own process, so earlier sealed sessions and prompt history read there; `/lock` drops them again, and so does an idle lock after 15 minutes without a key typed at the terminal (output, timers and the agent never count), which the terminal announces. The terminal opens no WebSocket listener in secure mode, which the secure table refuses and which would otherwise have stopped it from starting; plain mode keeps its listener. An `open` link starts the terminal the same way, and the direct `user-local` command is no longer mistaken for print mode when it is combined with `-p`. A missing or unreadable keyring file still refuses every conversation store, and nothing falls back to plaintext. `secure lock` still reaches live runtimes only; a terminal's keys close with `/lock`, the idle lock or its exit.
